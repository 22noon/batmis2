# BatMIS occurrence-checkpoint spacing experiment

## Summary

The current 256-row spacing remains a reasonable default. Reducing it to 64
or 128 rows produced rank-replay and full-search results within the observed
variation of the 256-row build. Increasing it to 512 or 1024 reduced the
occurrence-table footprint, but slowed rank replay by 2.24×/3.13× and mapper
search by 52%/81%, respectively, on this workload.

The experiment changed no production source, index format default, or mapper
behavior. Variant sources and indexes were isolated under `/tmp`. For the
512/1024 builds, correctness required two benchmark-only adaptations: the
existing SIMD `BWTDecode()` was called in aligned chunks, and the checkpoint
table builder used direct packed-symbol counting. The decoder primitive and
search algorithm were not replaced. Those variants therefore measure the
larger spacing together with the necessary decode chunking.

## Source audit

In [`index/BWT.h`](../index/BWT.h:50), the format uses 16-bit minor counts,
pairs two minor checkpoints into a 32-bit word, places major counts every
65,536 rows, and defaults `OCC_INTERVAL` to 256. `BWTGenerateOccValueFromBwt()`
in `index/BWTConstruct.c:800–990` generates each checkpoint; the loader
derives the table sizes from the compile-time constants. The `.fmv` header
contains the primary row and cumulative counts, but no checkpoint-spacing
identifier. A given `.fmv` must therefore be loaded by a binary built for the
same spacing.

`BWTOccValue()` (`index/BWT.c:539–568`) adjusts rows after `inverseSa0` down by
one because the sentinel row is not encoded. It rounds the adjusted row to
the nearest checkpoint using `(index + OCC_INTERVAL/2 - 1) / OCC_INTERVAL`,
loads the explicit count, and adds or subtracts the count between the
checkpoint and row. `BWTOccValueExplicit()` (`index/BWT.c:802–811`) combines a
major count with a 16-bit minor count. `index/BWT.c:847–858` sizes the minor
and major tables from the spacing and the 65,536-row major period.

`BWTDecode()` (`index/BWT.c:315–538`) compares packed two-bit symbols with
SSE2. It loads two aligned 128-bit vectors, each holding 64 symbols, masks the
end portions and reduces the matching lanes. With the default nearest
checkpoint policy, at most 128 rows separate a query from its checkpoint;
that fits the decoder's two-vector span. Expected maximum decode spans are:

| Checkpoint spacing | Maximum rows between checkpoint and query |
|---:|---:|
| 64 | 32 |
| 128 | 64 |
| 256 | 128 |
| 512 | 256 |
| 1024 | 512 |

For 512/1024, the unmodified decoder cannot cover the full span. Also, the
legacy generator's packed-byte overflow exception adds exactly 256 counts
(`BWTConstruct.c:846–884`); it is not valid for a single 512/1024-row minor
interval that can contain more than 255 occurrences of a base. The isolated
wide-spacing builds consequently split the decode into aligned, at-most-128
row calls to the existing `BWTDecode()` and build their occurrence checkpoints
by direct packed-BWT counting. The 64/128/256 builds use the existing decoder
and generator with only the compile-time spacing changed.

## Build and correctness method

Environment: GCC/G++ 13.3.0, Linux 6.17.0-19-generic, Intel Core Ultra 7
165H. All variants used `-w -O3 -funroll-loops -maccumulate-outgoing-args
-msse2 -g -O2` (effective `-O2`), with the same C++17 mode and no LTO. Each
spacing had its own temporary source, binary and index directory. The
reproduction helper is
[`prepare_occ_spacing_variants.py`](prepare_occ_spacing_variants.py); it
copies sources into the build directory, applies the isolated spacing
configuration, builds the mapper/index utility, generates an index and rank
trace, and runs the exhaustive rank oracle. Commands used:

```sh
python3 benchmark/prepare_occ_spacing_variants.py \
  --repo "$PWD" \
  --build-root /tmp/batmis_checkpoint_repro \
  --reference /tmp/zero_min_exp1/ref.fa \
  --reads /tmp/zero_min_exp1/reads_100k.fq

python3 benchmark/run_occ_spacing_trials.py \
  --build-root /tmp/batmis_checkpoint_spacing \
  --reads /tmp/zero_min_exp1/reads_100k.fq \
  --trace /tmp/batmis_checkpoint_spacing/rank_trace.bin \
  --trials 10 \
  --rank-output benchmark/occ_spacing_rank_trials.jsonl \
  --mapper-output benchmark/occ_spacing_mapper_trials.jsonl
```

The reference SHA256 is `820adc6c0960567688d20e8cc4c775c4c6cfedfab893755d76e50938db940b6a`;
the reads SHA256 is
`a6adffaf0ca4718a0a00b3d1b8378503b39d31130608d1a684a030b9a347f4fd`. All
variants produced the same `.bwt` SHA256
`140087efc5f2260ded757e61c64a1222edf368aae19b73bbd01d79c40eb397ad`. Each
`.fmv` was generated by its matching variant's index builder.

The direct rank oracle checked all 200,001 row positions, including row zero,
the row at `inverseSa0` and its neighbors, all checkpoint edges and the final
row, for all four symbols: 800,004 queries per spacing. Expected values were
computed by scanning packed BWT symbols after applying the sentinel adjustment.
All five passed. Full mapper TSV output for each spacing was byte-identical to
the minimized 256-row baseline, SHA256
`4412d1193a1aebc82e7266b2b101580f67dcb475ad3016ddd438868a6fdf6e48`; all runs
reported 100,000 records and 75,000 hits.

The output comparison was run outside timing with:

```sh
for s in 64 128 256 512 1024; do
  /tmp/batmis_checkpoint_spacing/$s/batman_zero_structured \
    -q /tmp/zero_min_exp1/reads_100k.fq \
    -g /tmp/batmis_checkpoint_spacing/$s/ref.fa -m 0 \
    -o /tmp/batmis_checkpoint_spacing/$s/output.tsv
  cmp /tmp/batmis_structured_build_matched/100k.baseline.tsv \
    /tmp/batmis_checkpoint_spacing/$s/output.tsv
done

The rank trace was generated once from the 256-row exact-search traversal and
replayed unchanged for every variant. Its 8-byte entries record the input row,
base and whether the query came from a singleton or multi-row extension. It
contains 8,046,000 rank requests: 7,304,000 singleton-origin and 742,000
multi-row-origin endpoint requests. Trace SHA256:
`0a245d4c64e0e958e44cdf18f1cce9943561bc9dad5b43bb3b41602340591450`.
`replay_occ_spacing_rank.cpp` loads the index and trace before timing, then
times only the rank loop and consumes all answers in a checksum.

Each phase used ten trials with a warm-up per spacing. Configuration order
rotated through all five positions and was reversed for the second set of five
trials. Load average ranged from 1.88 to 2.05. The runner records exact
commands, binary/index/input hashes, elapsed times and load samples.

## Index size and construction

variant. The `.fmv` file includes a 20-byte header; in-memory occurrence-table

Index-build wall times on this small reference were approximately 0.026–0.030

[`occ_spacing_index_build_trials.jsonl`](occ_spacing_index_build_trials.jsonl)
for commands, hashes, sizes and measured times. These index-build times are
not representative of a large reference.

The 64/128 changes are smaller than run-to-run variation and their ranges
overlap broadly with 256. The larger spacings were slower in all ten paired
trials. Parsing, index load and seed-table times are available per run in the
mapper JSONL; as expected, they are small relative to search on this workload.

## Interpretation and recommendation

1. **Smaller spacing:** 64/128 did not provide a repeatable rank-replay or
   mapper improvement over 256. 128 had the best median replay by 0.15 ms, but
   2/10 paired trials favored it; the difference is not robust evidence of a
   useful gain.
2. **Larger spacing:** occurrence tables shrink substantially, but decode span
   and the number of decoder calls increase. The time cost outweighed the
   memory reduction on this workload.
3. **Full search:** replay and mapper results agree directionally: 512/1024
   are slower; 64/128/256 form a near-flat region. Replay magnifies the large
   spacing cost because it times rank calls alone, while mapper search also
   includes encoding, branches and interval bookkeeping.
4. **Cache/branch causes:** no cache or branch conclusion is supported.
   Hardware counters remain unavailable (`perf_event_paranoid=4`; the
   installed kernel-matched perf tool is missing). Reduced table size is
   measured, but improved cache behavior is not.

Keep 256 as the default. The smallest useful follow-up is to repeat the
rank-trace replay and full mapper benchmark on a larger reference, where the
occurrence tables are large enough for the memory-footprint trade-off to be
meaningful, on a host with hardware cache counters available.
